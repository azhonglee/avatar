# Avatar 产品化架构（前后端）

本文档说明在可靠性底座（见 [可靠性设计](可靠性设计.md)）之上补齐的产品级前后端架构，涵盖统一命令层、本机 Web 控制台、飞书交互卡片、交付闭环、设置/体检/通知偏好、用量预算与分诊反馈。

## 1. 总览：一条命令链路，两个入口

- **飞书是主场**：80% 的高频操作在飞书交互卡片上点一下完成（手机同样可用），一个对象一张卡片原地更新，不刷屏。
- **本机 Web 控制台是深度**：查看时间线、实时日志、完整 diff、审查全文、用量趋势、健康队列、修改设置与初始化向导。
- **所有入口共用统一命令层**（`src/commands.ts`）：飞书卡片按钮、控制台按钮、私聊指令、CLI 都走 `Commands.exec`，统一做 zod 校验、前置条件检查、写入 `audit` 表，再把意图落入账本。

```
飞书卡片按钮 (card.action.trigger → inbox) ──┐
本机 Web 控制台 (POST /api/commands/:name) ──┼──▶ Commands.exec (校验 + 审计) ──▶ Ledger (work 表)
私聊机器人 (/do /brief ...) / CLI (pa command)┘                                      │
                                                                                     ▼
Web 控制台 ◀── REST API + SSE (/api/events) ◀── Bus ◀── Engine (dispatch / delivery / job / effect)
                                                                                     │
飞书交互卡片 (card.upsert → 原地 patch) ◀─────────────────────────── Outbox + 通知偏好门控
```

## 2. 后端模块

模块注册集中在 `src/modules.ts`，模块之间通过 `app.commands`、`app.ext`、`app.bus`、`app.effectHooks` 交互，不直接互相耦合。

| 模块 | 文件 | 职责 |
|---|---|---|
| 命令层 | `src/commands.ts`、`src/core-commands.ts` | 核心命令（`dispatch.create/cancel/retry/rework/switch_harness`、`work.retry/acknowledge`、`job.run`）、`availableActions` 按钮策略、命令审计 |
| HTTP API + SSE | `src/server/index.ts`、`src/api/types.ts`、`src/api/queries.ts` | 本机 REST + SSE + SPA 静态服务；`server.token` 令牌鉴权（`/login?token=` → `HttpOnly + SameSite=Strict` Cookie，或 `Authorization: Bearer`）；写请求同源校验 + JSON 强制；日志路径限制在 `data_dir` 内 |
| 飞书交互卡片 | `src/cards/` | schema 2.0 卡片模板（候选任务、派单进度/结果原地更新、失败告警、早晚报、`/do` 表单）；`card.action.trigger` 回调只认主人、通过 `store.once` 幂等去重；进行中变化按卡片去抖合并，终态立即刷新；卡片/私信自身投递失败不发告警（防循环） |
| 交付闭环 | `src/delivery/` | `delivery.create_pr`（推送 `pa/<id>` 分支，先查重再创建；支持 GitHub REST v3、GitLab REST v4、公司 Codebase via `bytedcli codebase mr`；支持草稿）、`delivery.merge_local`（仅快进更新，工作区脏或无法快进时拒绝并给建议）、`delivery.discard`（立即标为已放弃，保留 `discard_retention_days` 天后再清理 worktree 与本地分支）、`delivery.restore`（保留期内恢复并取消清理） |
| 平台服务 | `src/settings.ts`、`src/doctor.ts`、`src/notify-prefs.ts`、`src/platform.ts` | 设置读写（用 `yaml` Document API 保留注释和顺序；明文 env 打码；原子写 + `.bak`；可热加载段原地同步到 `app.cfg`，冷字段标记 `restart_required`；禁止经 API 改 `data_dir`/`bins`）；结构化体检 `pa doctor` / `/api/doctor`；通知偏好（按类型开关、支持跨午夜的免打扰时段、失败告警永不拦截、已有卡片的原地更新不延后） |
| 用量与分诊反馈 | `src/usage.ts`、`src/candidates.ts` | 从 `acpx --format quiet` 的 stderr（`[acpx] tokens:` / `[acpx] cost:` 及常见 JSON 字段）解析 token 与费用，记入 `steps` 表；每日与单任务（按卡片汇总）预算守卫，超限暂停派单为 `needs_human/budget`；候选任务确认/驳回/直接派单命令、准确率统计、最近 8 条反馈样例回填 `prompts/triage.md` 校准分诊 |

## 3. 本机 Web 控制台（`web/`）

React 19 + Vite + TypeScript 单页应用，直接引用 `src/api/types.ts`（不重复定义契约），手写 CSS（`:root` 变量 + `prefers-color-scheme` 亮/暗主题，响应式下探至 380px），产物构建到 `web/dist/` 由常驻进程托管。

| 路由 | 页面 | 内容 |
|---|---|---|
| `/` | 概览 | 需要处理（需介入 / 待验收 / 待确认 / 失败）、进行中派单、今日花费与预算条、常驻进程健康状态、体检未就绪横幅 |
| `/dispatches` | 派单列表 | 按状态筛选、搜索、新建派单对话框 |
| `/dispatches/:id` | 派单详情 | 阶段与验收摘要、按 `actions` 驱动的操作栏（取消/重试/带意见返工/换执行者/创建 PR/合并/放弃/恢复，破坏性操作带确认框）、步骤时间线 + 实时日志尾随、每轮校验/审查全文、可折叠 unified diff、飞书写回状态、历史派单与审计 |
| `/candidates` | 候选任务 | 分诊记录、来源摘录、置信度、准确率统计，一键确认 / 驳回 / 派单 |
| `/jobs` | 作业 | 定时作业列表、下次执行时间、上次结果、立即运行 |
| `/health` | 健康 | 重试中与已失败的事件/飞书写入/作业/交付，一键重试或忽略；守卫拦截审计 |
| `/usage` | 花费 | 按日柱状图、按 harness 汇总、花费最高任务、预算状态（未上报 token 时提示仅记录耗时） |
| `/settings` | 设置 | 可编辑配置表单（删除项自动发 `null` 补丁移除 YAML 键）、字段级校验错误、热生效与需重启提示 |
| `/setup` | 初始化向导 | 调用 `/api/doctor` 逐项展示状态与 Markdown 修复指引 |

## 4. 联调与验证清单

以下项目已用桩和本地仓库完整验证，接真实外部系统时需按清单确认：

1. **飞书开发者后台**：除原有的 4 个事件外，启用交互卡片需额外开启 `card.action.trigger`（长连接，bot 身份），并确保本机 `lark-cli ≥ 1.0.100`。
2. **飞书卡片更新接口**：`upsertCard` 调用 `im messages patch` 原地更新卡片；若失败会自动回退为重发一张新卡。
3. **Codebase MR CLI**：`src/delivery/providers.ts` 调用 `bytedcli codebase mr create`（含 `--json`），接真实仓库前建议先对测试仓库试跑一次确认返回 JSON 字段。
4. **acpx 用量输出**：`parseUsage` 按 `openclaw/acpx` 的 `--format quiet` stderr 格式解析；若所用适配器不上报 token，系统仅记录步骤耗时并在花费页显示“仅记录耗时”，不影响主流程。
