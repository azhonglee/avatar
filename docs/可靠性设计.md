# 可靠性设计：账本、对账与验收关卡

本文说明 personal-agent 如何保证“能重启就能续跑”、“完成就是达标”。实现见 `src/ledger.ts`、`src/engine.ts`、`src/effects.ts`、`src/workflows/dispatch.ts`。

## 1. 要解决的问题

| 现象 | 根因 |
|---|---|
| 重启后派单卡在「Agent进行中」，没人再管 | 工作进度分散在看板列、内存 Promise、运行记录三处，没有一处能说清“做到哪一步了” |
| 事件处理失败就永久丢失 | 边沿触发：正确性依赖“每个事件恰好被成功处理一次” |
| 返工耗尽仍记为成功、进“待验收” | “执行结束”与“任务达标”被当作同一件事 |
| 审查器故障被当作打回；正文出现 `VERDICT: APPROVE` 会误判通过 | 决策信号是自由文本，判定散落在流程代码里 |

## 2. 原则

1. **本地账本是唯一事实来源，飞书看板是投影。** 看板上的操作被解释为意图：拖进“派给Agent”= 派单，把进行中的卡片拖走或完成 = 取消。
2. **水平触发 + 对账。** 事件只是“该看一眼”的提示；定时对账比较看板与账本，丢事件只会变慢，不会出错。
3. **先记意图再动手。** 外部输入先进 inbox；对飞书的写操作作为 outbox 记录，与状态迁移在同一个 SQLite 事务里提交，再由发布器幂等投递。
4. **长流程是带检查点的状态机。** 租约表示归属，心跳续约；崩溃后租约过期（或同机判定持有者已死）即被接管，从最后的检查点继续。
5. **完成由验收关卡定义。** 结果分为 通过 / 未验证 / 需人工介入 / 执行出错 / 已取消，看板列由结果推导。

## 3. 结构

```
输入（飞书事件 / 消息轮询 / 看板拖动 / cron）
   │ 落库（幂等入队）
   ▼
账本 work 表 ── kind: event | effect | dispatch | job
   │ 引擎：领取（租约 + attempts+1）→ 执行 → transition（fencing）
   ▼
outbox（kind=effect）── 发布器按工作内顺序投递 ──▶ 飞书（评论 / 移卡片 / 私信）
```

- **work 表**：`state` / `terminal` / `outcome` / `attempts` / `next_at` / `lease_owner` / `lease_until` / `cancel` / `payload`。
- **steps 表**：每次 harness / 校验命令的执行记录（含进程组 pid），用于审计和崩溃后清理遗留进程。
- **fencing**：所有 `transition` 都要求仍持有租约，失去租约的旧执行者写不进任何进度或副作用。
- **持有者身份**：`主机:pid:随机串`。同机上 pid 已不存在、或 pid 相同但随机串不同（容器里 pid 复用），即判定为已死，立即收回其租约。

### 各类工作的语义

| kind | 语义 | 重试 | 耗尽后 |
|---|---|---|---|
| event | 飞书事件；处理器都是幂等的 | 退避重试 `engine.event_attempts` 次 | `dead`，私信告诉你 |
| effect | 飞书写操作；评论重试前先查重、私信带幂等键、移动本身幂等 | 退避重试 `engine.effect_attempts` 次 | `dead`，晨报和 `pa status` 提示 |
| dispatch | 派单状态机 | 同一状态最多 `dispatch.max_attempts` 次（含崩溃中断） | `errored`，评论原因并移到“需人工介入” |
| job | agent 作业（会写飞书，不能保证幂等） | **至多一次**：中断不重跑 | `errored`，私信说明可能执行了一部分 |

私聊机器人：指令（`/brief` `/capture` `/dispatch` `/do` `/status`）都是幂等的（`/do` 以消息 id 为幂等键建任务）；回复先存再发，发送失败重试时不会再执行一遍；自由对话属于 agent 作业，中断后提示你重发而不是悄悄重跑。

## 4. 派单状态机

```
queued ──准备（读卡片、选执行者/审查者、建 worktree）──▶ executing(n)
executing(n) ──记录检查点 → worker → 自动提交──▶ verifying(n)
verifying(n) ──校验命令 → 交叉审查 → 验收关卡──▶ executing(n+1) | accepted | unverified | needs_human
任意非终态 ──卡片被拖走──▶ cancelled        重试耗尽 ──▶ errored
```

- **git 检查点**：每轮开始前提交快照并把 HEAD 记进 payload（先落库再动手）；崩溃或失败后重跑这一轮时先 `git reset --hard <检查点> && git clean -fd`，丢掉半成品，起点确定。每轮结束自动提交，审查看的是相对基线的完整 diff。
- **遗留进程**：harness 以独立进程组运行，pgid 记在 steps 里。接管时结束前任遗留的进程组，避免两个执行者同时改一个 worktree；优雅退出时也会结束它们，并且不计入尝试次数。
- **取消**：对账发现卡片离开“派给Agent / Agent进行中”（被拖走、完成或删除）即请求取消；心跳看到后结束 harness，随即收尾为 `cancelled`，改动保留在 worktree。

## 5. 验收关卡

```
有校验器故障（审查超时/无输出/结论无法解析，命令无法运行）→ 需人工介入（故障 ≠ 打回，不消耗返工轮次）
有校验不通过 → 还有返工轮次就带着意见返工，否则需人工介入
没有任何校验 → acceptance.on_unverified：needs_human（默认）或 review（标为未验证进待验收）
全部通过     → 通过，进“待验收”
```

- 确定性校验优先：`dispatch.repos.<别名>.verify` 配置的命令在 worktree 里运行，失败就不再花钱做 LLM 审查，直接返工。
- 审查输出结构化 JSON（`prompts/review.md`），用 zod 校验；兼容旧格式时只认**最后一个非空行**的 `VERDICT:`。
- 审查器故障先重试 `acceptance.review_retries` 次。
- 早晚报按 outcome 统计派单，而不是按进程退出码。

## 6. 对账

`Dispatcher.reconcile()`：启动时、每 `schedules.dispatch`、任务变更事件提示时、`/dispatch` `/do` 时运行。

**两次列表读取不是同一个快照。** Avatar 自己把卡片从“派给Agent”移到“Agent进行中”时，可能先读到移动前的“进行中”、再读到移动后的“派给Agent”，两列都看不到这张卡片；翻完所有页也挡不住这种时序。所以列表只用来发现**候选**，凡是不可逆的决定都按任务 ID 核实（`Board.locateTask`：任务详情里的完成状态和所在分组）：

| 候选 | 判定 |
|---|---|
| “派给Agent”里从没派过的新卡片 | 直接新建派单（读漏了只是晚一轮） |
| 上一次派单已终结（且其飞书写入都已落地），卡片又出现在“派给Agent” | 核实确实在“派给Agent”才再派——防止旧快照触发重复派单 |
| 未终结的派单，两列都没看到 | 核实已完成、已不在本看板、或在其他列才取消；核实发现仍在两列之一就忽略 |
| 按 ID 查不清（接口失败、结构无法识别、缺少分组信息） | 不做决定，留到下次对账 |

同一张卡片同时至多一项未终结派单由数据库唯一索引保证；列表仍然翻完所有页，减少需要核实的候选。

## 7. 已知边界

- 建任务、发评论这类没有幂等参数的接口，在“调用成功”与“记下结果”之间崩溃仍可能重复一次（建任务用 kv 记录结果、评论重试前查重，把窗口压到最小）。
- 同一台机器以外的执行者无法判定死活，只能等租约过期（`engine.lease_sec`）。
- 卡片被删除时按 ID 查询会失败，按“查不清”处理：这次派单不会被取消，会跑完并在写评论时失败（outbox 重试耗尽后记为 dead）。
- 飞书接口的真实返回结构（尤其 `task tasks get` 的 `completed_at` / `tasklists`、`task comments list`、`task sections tasks` 的分页字段）需在开发机联调确认；字段对不上时对账会一直“留到下次”而不会误取消，日志里有“无法按任务 ID 核实”。
