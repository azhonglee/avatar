# 飞书个人 Superagent 方案

> 目标：在后台静默运行一个个人 agent，持续整理飞书个人知识库、识别和追踪任务、按时提醒，并能把具体工作派给不同的 coding harness（Claude Code / Codex / Gemini / DeepSeek Harness / Doubao 等），由 superagent 统一调度、交叉审查。

## 一、前提（已确认）

- 合规：允许把飞书数据发送给外部模型。
- 运行环境：远程开发机（常开）。
- 可用 harness：Claude Code、Codex、Gemini、Doubao、DSH（DeepSeek Harness）等。

## 二、核心结论

**飞书是唯一的数据层和界面；一个轻量常驻进程做 superagent；其他 harness 通过 ACP 按需调起，做完即退出。**

三条设计原则：

1. **状态只存在飞书里**（任务、看板、知识库），不存在 agent 记忆里。换 harness 不丢东西，人随时看得见、改得了。
2. **只有 superagent 写飞书。** worker harness 不拿飞书权限，只交回结果，由守护进程写回。权限最小，也没有多 agent 写冲突。
3. **能用确定性代码就不用模型。** 事件接收、去重、看板流转、晨报都是普通代码；只有“判断是不是任务”“整理知识库”“干活”才用模型。

## 三、架构

```
┌──────────────── 飞书（业务数据 + 界面）──────────────────┐
│ 任务清单「Agent 看板」  Inbox│待确认│派给Agent│Agent进行中│待验收│需人工介入│等待他人 │
│ 知识空间「个人知识库」  00 Inbox / 会议纪要 / 项目 / 主题 / 变更日志 │
│ 机器人私信            晨报·晚报·作业结果·私聊指令                │
└──────────────▲───────────────────────────────────────────┘
               │ lark-cli（--as user 读写你的数据；--as bot 只给你发消息）
┌──────────────┴──── personal-agent 常驻进程（远程开发机）────┐
│ 事件长连接：私聊机器人 / 任务变更 / 文档评论@我 / 妙记生成      │
│ 定时：每 15 分钟识别任务，每 5 分钟扫描派单列，早晚报，每周整理  │
│ superagent（brain harness）：分诊、私聊对话、知识库作业         │
│ 守卫：agent 调 lark-cli 先过策略（读放行、写白名单、禁删禁外发） │
│ 本地 SQLite 账本：派单/事件/作业/飞书写入的进度与租约（工作状态的唯一事实来源）│
└──────────────┬───────────────────────────────────────────┘
               │ acpx（ACP，统一的无头调用方式）
   claude · codex · gemini · deepseek-harness · doubao（trae 或自定义）
   每个代码任务一个独立 git worktree；执行者与审查者必须是不同 harness
```

## 四、组件选型

| 组件 | 作用 | 理由 |
|---|---|---|
| 飞书官方 lark-cli | 以本人身份（OAuth）读写任务、知识库、文档、消息、妙记；`event consume` 收事件 | 官方主推，覆盖面最全；长连接收事件，无需公网 IP；自带 skills，任何 harness 都能读 |
| acpx | 用同一种命令调用 30 多个 ACP harness | 不必为每个 harness 写适配；支持权限模式、超时、一次性和持久会话 |
| Node.js 22 + TypeScript | 常驻进程 | 与 lark-cli、acpx 同一运行时；依赖只有 yaml、croner、zod |
| SQLite（Node 内置） | 本地状态 | 零依赖；只存不该放进飞书的东西 |

没有选的方案：

- **飞书 aily**：零运维、合规，但难以调度开发机上的本地 harness，行为不可审计、不可定制。可作为日常补充。
- **OpenClaw 作为底座**：功能全，但今年安全事件多（多个高危 CVE、ClawHub 恶意 skill），体量大、变化快。我们只借用其团队的 acpx。
- **Hermes Agent**：自学习有亮点，但深度操作飞书仍要靠 lark-cli，集成面窄。

## 五、五条流水线

### 1. 感知

| 信号 | 方式 |
|---|---|
| 你私聊机器人（指令/提问） | 事件 `im.message.receive_v1`（机器人身份） |
| 任务变化 | 事件 `task.task.update_user_access_v2`（本人身份）→ 尽快扫描派单列 |
| 文档评论 @我 | 事件 `drive.notice.comment_add_v1`（本人身份） |
| 妙记生成 | 事件 `minutes.minute.generated_v1`（本人身份） |
| 群聊 @我、私聊里别人的请求 | 机器人收不到，每 15 分钟以本人身份增量搜索（`im +messages-search`） |

### 2. 任务识别

信号进入本地队列 → 批量交给 brain 分诊（**不给任何工具、不给飞书权限**，只输出 JSON）→ 置信度 ≥ 0.9 直接进 Inbox，0.6～0.9 进“待确认”，更低只记录。任务描述里带来源链接、判断依据、原文摘录和信号 ID，便于追溯和去重。agent 不会替你回复别人，也不会给别人派任务。

### 3. 看板、进度和提醒

- 看板 = 飞书任务清单「Agent 看板」，分组即列。“已完成”用任务完成状态表示。
- 截止提醒用飞书任务原生提醒（最可靠）；agent 负责工作日早晚的概览私信：逾期、今天/明天截止、待确认、待验收、过去 24 小时 agent 做了什么。
- 拖动卡片不产生事件，所以派单列靠每 5 分钟扫描，任务变更事件只是让扫描提前。

### 4. 知识库

- agent 只写知识空间「个人知识库」，不改别人的文档、不删除、不移动；每次改动在「变更日志」记一笔，出错可用文档历史版本回滚。
- 妙记生成后自动整理成「会议纪要」下的一篇文档。
- 每周五下午整理一次：归类 Inbox、更新《索引》、列出重复/过期文档给你决定。
- 暂不建向量库：索引页 + 飞书搜索足够，等真的找不到再加检索。

### 5. superagent 与多 harness 协作

- **派单约定**：把任务拖到“派给Agent”列即可。标题前缀 `[codex]` 指定执行者（缺省用配置的默认执行者）；描述里写 `repo: 别名` 则在该仓库的独立 git worktree 分支 `pa/<任务ID>` 上执行。也可以私聊机器人 `/do [codex] 修复登录页报错 repo: web`。
- **执行 → 校验 → 交叉审查 → 返工 → 验收关卡**：执行者干完后，先跑仓库配置的校验命令（可选），再由另一个 harness 只读审查（执行者恰好是 reviewer 时自动换成 brain），输出结构化结论；不通过则带着意见返工。只有通过验收才移到“待验收”；返工耗尽、审查器故障、没有任何校验或执行反复失败，都移到“需人工介入”。每一步都写成任务评论，合并由你决定。崩溃后从检查点续跑，详见 [可靠性设计](可靠性设计.md)。
- **路由先用固定规则**（标题前缀 / 默认执行者），不让模型自己选 harness；等观察到明确的能力差异再改。
- 多 harness 的价值在于能力互补和交叉验证；单个任务没有这两点时，不必拉多个 harness。

## 六、安全设计

1. **守卫**：任何 harness 调 lark-cli 时，PATH 里排在前面的是守卫脚本，按角色放行：
   - 分诊、worker：一律拒绝（不碰飞书）。
   - superagent 作业：读操作放行；写操作只放行白名单（建/改自己的任务与文档、给主人本人发消息）；删除、移动、改权限、指派他人、给他人发消息、登录配置一律拒绝。
   - 每次调用记入 `guard.log`，可审计。
2. **提示注入**：别人的消息和文档都当作不可信数据；分诊这一步没有任何工具，注入也做不了事。
3. **高风险确认**：lark-cli 退出码 10（高风险写操作）不会被自动绕过，交给人处理。
4. **机器人只听主人**：只处理主人私聊发来的消息，其他人的一律忽略并记录。
5. **代码隔离**：每个代码任务一个 worktree，不 push、不动其他分支，合并由你决定。

## 七、部署（远程开发机）

1. 安装 Node ≥ 22.13、git，以及要用到的 harness（claude、codex、gemini、dsh 等）并各自登录好。
2. 安装工具：`npm i -g @larksuite/cli acpx`，再执行 `npx skills add larksuite/cli -y -g`（给 harness 装官方 skills，可选）。
3. 飞书应用：`lark-cli config init --new` 建自建应用；在开发者后台开启“刷新 user_access_token”（否则约 2 小时后失效）、在“事件与回调 → 长连接”里开启上面 4 个事件并发布版本；`lark-cli auth login --recommend` 以本人身份登录。
4. 部署本项目：`npm install`，`cp config.example.yaml config.yaml` 并修改，`bin/pa doctor` 检查，`bin/pa init` 建看板和知识空间。
5. 常驻：有 systemd 用 `deploy/personal-agent.service`；没有 systemd 用 `deploy/run-forever.sh`（或 tmux）。
6. 可选的个人 Web 实时通道需要另行部署独立网关 `bin/feishu-gateway`（`deploy/feishu-gateway.service` 以独立 OS 用户运行，或 `deploy/Dockerfile.gateway`、`deploy/feishu-gateway-forever.sh`），步骤见 [工作上下文](工作上下文.md) 第 6 节。

## 八、成本与运维

- 主要花费在派单执行（取决于任务量）；分诊每 15 分钟最多一次，只在有新信号时调用；晨报不调用模型。
- 日志：常驻进程输出 JSON 行日志；每次 harness 调用的完整提示词和输出在数据目录 `runs/` 下；守卫审计在 `logs/guard.log`。
- `pa doctor` 一键检查依赖、登录和初始化状态；私聊机器人发 `/status` 看最近 24 小时运行情况。

## 九、已知限制与待联调项

- 框架已用桩程序做过端到端测试，但飞书各接口的**真实返回结构**需在开发机上联调确认（代码里按字段名宽松解析，问题会集中在 `src/board.ts`、`src/workflows/capture.ts`）。
- 飞书任务清单是否有拖拽式看板视图需在客户端确认；不满意可改用多维表格看板。
- lark-cli 里有“任务智能体”接口（`register_agent`、`append_task_steps`），可能让每个 harness 以执行者身份出现在任务里并留下步骤记录，文档不全，留待验证。
- Doubao 的接入方式（TRAE CLI 或 Claude Code + 方舟兼容端点）需按实际环境配置。
- acpx 尚未到 1.0，接口可能变化；调用集中在 `src/harness.ts` 一处，便于替换。

## 十、路线图

- **已完成（基础框架）**：事件长连接守护、定时调度、任务识别、看板初始化与流转、派单 + 交叉审查 + 返工、早晚报、私聊指令、知识库作业（妙记纪要、每周整理）、lark-cli 守卫、本地状态与审计、部署脚本、测试。
- **下一步**：真实环境联调 → 观察一周分诊准确率并调阈值 → 交互卡片（一键确认/忽略）→ 多维表格仪表盘（成本、成功率）→ 按需加检索与自动路由。
